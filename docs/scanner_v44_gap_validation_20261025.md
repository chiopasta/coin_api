## 1. 범위와 분모

V4.3의 두 거래소 ENA·ETH·FLOCK·SAND, 2026-10-24 **23:50·23:55 KST** 격자를 재현했다.
BTC는 benchmark이므로 신호 대상 분모에 넣지 않았다. 각 격자의 판단 직전 `[t-30분,t)` UTC 봉 시작 시각을 검사했다.
이는 **LOOKBACK_30M**이며 신호 이후30분 가격 평가가 아니다.

|측정 단위|분자/분모|의미|
|---|---:|---|
|완전 격자|4/16 =25.00%|4알트×2격자×2거래소 중 실제30개 분봉이 모두 있는 격자|
|중복 포함 minute slot|380/480 =79.17%|16격자×30분, 겹치는 분은 각 격자에서 다시 센다|
|고유 calendar minute|220/280 =78.57%|8거래소-종목쌍×23:20~23:55의35분, 겹치는 분은 한 번만 센다|

따라서 결측은 **100개 slot / 60개 고유 분 / 영향을 받은12개 격자**다.
개별 분봉의 보유율과 완전 격자 비율을 같은 지표처럼 비교하지 않는다.
기존 coverage의 observed·missing 목록을 재계산하고 core Series의 마감 시각 기반 range 가능 여부와 대조했다.
저장 집계 불일치·core range 완성도 불일치는0건이다. 4/16을 보고서 숫자로 가정한 것이 아니라 저장값과 별도로 재구성했다.

실제 수집 문제는 필요한 봉을 받지 못하거나 받은 봉을 저장하지 못하는 경우다.
이번에는 그 증거가 없었다. 반면 기존 정책은30분 중 한 분이라도 실제 봉이 없으면 range를NULL로 만든다.
무거래 분 때문에 평가가 불가능해지는 것은 **동결 정책의 제약**이며 계산 오류는 아니다.
이를 완화해 완성도를 높이는 변경은 이번 범위에서 하지 않았다.

## 2. 무거래 판정 증거

2026-10-25 **00:13:21.036~00:13:28.012 KST**에 별도 공개 API를 제한 조회했다.
사전 한도36회/120초/재시도0/직렬 간격0.3초, 실제 **24회 모두200, 오류0**이다.
대상은 결측이 있던 각 거래소 ENA·FLOCK·SAND뿐이다. [고정 한도](../reports/scanner_v44_20261025/bounds.json).

- 1·5·15분봉: 6거래소-종목쌍×3단위 =18회, 응답 각200봉. UTC/KST·단위·마감·정렬·중복·원천 거래대금 범위 검사를 통과했다.
- 별도 체결 목록: 6쌍×1페이지 =6회, 각500행. 모두23:20보다 오래된 체결까지 반환돼35분 진단 범위를 포함했다.
  실제 범위 내 체결은1,176행이었다. 페이지가 충분하지 않은 경우 추가 한도를 넘겨 조회하거나 부재를 확정하지 않도록 구현했다.
- 결측 분은 재조회1분봉에도 없었고 **해당 분의 체결도 없었다**.
  주변에 실제 거래가 있는 **150개 분봉**은 체결 가격의 고저가와 `Σ체결가격×체결수량`이 원천 분봉과 일치했다.
  거래대금 오차 기준은 기존 `max(1원, 원천 거래대금×1e-8)`이며 모두 통과했다.
- 거래 목록의 시각·날짜가 캔들과 같은 범위인지 검증했다. 업비트 `to`는UTC, 빗썸 체결 `to`는KST이며
  날짜 offset도 각각 `days_ago`/`daysAgo`로 다르다. 빗썸 요청은KST 자정 이후 `daysAgo=1`이었다.
  원천 UTC timestamp와 사람이 읽는 UTC 날짜·시각도 일치했다.

따라서 NO_TRADE는 단순 candle API 부재가 아니라 **다른 공개 체결 endpoint의 범위 확인 + 주변 양성 데이터 합계 일치**에 근거한다.
거래소 내부의 모든 체결을 외부에서 독립 감사했다는 의미는 아니다. 빈/잘린 체결 목록, 시각 불일치,
양성 데이터 모순, 불명확한 pagination은 UNKNOWN 또는 BLOCKED로 남기도록 했다. 이번 대상에는 그런 미확정 분이 없다.

요청 시각 해석의 근거는 [업비트 체결 문서](https://docs.upbit.com/kr/reference/list-pair-trades),
[빗썸 체결 문서](https://apidocs.bithumb.com/reference/체결-내역-조회)다.
[업비트 분봉 문서](https://docs.upbit.com/kr/reference/list-candles-minutes)의 무체결 시 봉 미생성 설명은 참고하되,
그 문장만으로 개별 분을 NO_TRADE로 확정하지 않았다.

## 5. 후속30분·60분 준비 상태의 분리

아래는 **신호가 아닌 기존16개 진단 격자**를 기준으로 한 준비도다. 실제 신호·live_horizons 행은0개다.
시간이 지났다는 이유로 종료된 수집기의 미래 가격 자료가 생긴 것으로 간주하지 않는다.

|판정 시각|30분 준비도|60분 준비도|
|---|---|---|
|V4.3 종료23:56:07|16개 모두 EVALUATION_PENDING|16개 모두 EVALUATION_PENDING|

현재 저장 자료의 공통 verified_until은23:56이다. 진단 API도 과거 lookback 범위만 조회했다.
따라서 후속30·60분 가격 평가 가능 건은 둘 다0개이며, 이를 수집 실패나 NO_TRADE로 추정하지 않는다.
후속30분이 완전해도60분은 PENDING일 수 있음을 별도 테스트했다. 이 준비도는 실제 탐지 신호의 성과 통계가 아니다.

## 6. 수정 사항과 BEFORE/AFTER

**실제 수집기·탐지 정책 수정0건.** 이번 자료에서 수집·평가 오류가 확인되지 않아 고치지 않았다.
`scanner_gap_audit_v44.py`라는 별도 read-only 진단 도구와 선별 테스트를 추가했다.
기존 wrapper·collector·분봉 guard·점수 없음·threshold·label·NULL 정책은 변경하지 않았다.

진단에서는 source absence와 근본 원인을 분리하고, 독립 체결 범위·raw hash·원천 집계 대조를 요구하도록 했다.
또한 실제 빗썸 응답에서 **체결 ID 재사용**을 발견했다. 반환된500행 페이지마다 ENA12·FLOCK47·SAND68행이
이미 나온 ID를 재사용했으며 SAND에는 payload가 완전히 같은 추가 행도3개 있었다.
이는35분 바깥을 포함한 전체 응답 페이지의 수치다. 이를 자동 중복 제거하면 거래대금이 틀어질 수 있다.

진단기는 한 페이지의 행 중복도 자체를 보존하고 native 합계로 확인한다. ID 충돌이 있는 다중 페이지는
cursor 경계를 확정할 수 없어 NO_TRADE 증거로 거부한다. 이번에는6쌍 모두 한 페이지로 충분했다.
V4는 체결 API를 쓰지 않으므로 이 발견은 기존 분봉 저장 오류가 아니다. 원시 응답도 수정하지 않았다.
