# 선정 직전 24시간 coverage 검증

T = 2026-09-01 00:00 KST. 확인 범위는 [2026-08-31 00:00, 2026-09-01 00:00) KST.

기존 구현은 200봉 한 페이지만 사용하지 않았다. cursor가 T-24h 이하에 도달할 때까지
200봉씩 반복 조회하고, [T-24h,T) 안의 고유 timestamp만 집계해 1440으로 나눈다.
각 페이지의 최저 timestamp가 다음 exclusive `to`이며, timestamp 역전/중복/정체/미래 응답은 거부한다.

| 종목 | 페이지 | 응답 봉 | 범위 내 고유 분 | 분모 | coverage | 시작점 도달 |
|---|---:|---:|---:|---:|---:|---|
| KRW-BTC | 8 | 1600 | 1440 | 1440 | 100% | 예 |
| KRW-ETH | 8 | 1600 | 1440 | 1440 | 100% | 예 |
| KRW-XRP | 8 | 1600 | 1440 | 1440 | 100% | 예 |

응답의 이전 구간 160봉씩은 coverage 계산에서 제외했다. 총 실제 API 24회, retry 0,
이번 진단 실측 약 3.51초. 신규 캔들 DB 저장/전체 종목 선정/14일 수집은 수행하지 않았다.
페이지별 cursor와 최저/최고 timestamp는 prior_day_coverage_diagnostic.json에 보존했다.

## 변경

동일한 기존 조회 로직을 `prior_day_coverage()`로 분리하고 종목 선정에서 호출한다.
계산식과 95% 기준은 그대로다. 페이지 수/응답 수/고유 분수/시작점 도달 여부를
선정 로그와 manifest의 선정 근거에 추가했다.

mock 1440/1296/720봉은 각각 100/90/50%이며 8/7/4페이지를 조회하는 회귀 테스트를 추가했다.
T-24h 포함, T 제외, cursor 엄격 감소, 범위 밖 과거 봉 제외, 미래 응답 거부도 확인했다.

## 해석과 재실행

200/1440의 수치 유사성만으로 한 페이지 버그라 판단할 수 없다. 이 코드와 실제 3종목 검증에서는
그 버그가 확인되지 않았다. 낮은 coverage 종목을 추가 API 조회하지 않았으므로 그 종목의
공백 원인이 실제 무체결인지 API 원천 데이터 문제인지까지 확정하지 않는다.

95% 기준은 유지할 수 있지만 50종목 확보가 가능하다는 뜻은 아니다. 동일 T로 재실행하면
7/50 오류가 재발할 수 있다. 이번 변경은 조건 완화나 50종목 확보를 위한 수정이 아니다.
재실행 시 선정 API 비용도 다시 발생한다(선정 실패 시 manifest가 생성되지 않는 기존 정책).
